# Reflection- Portfolio 1A (LinkedList<T>)


I started with the Node struct and the basic operations first: pushFront, pushBack, popFront, remove, and contains, since those felt the most straightforward. I moved on to the Rule of Three next, and did the iterator last since it depended on the Node structure being solid first. I worked directly on ludwig, compiling after almost every change so I could catch mistakes early instead of writing the whole thing and debugging it all at once.

The part that gave me the most trouble was the Rule of Three, specifically the copy constructor and copy assignment operator. You informed the assignment turned out to be exactly right: it is easy to write a copy constructor that just copies the head pointer instead of actually copying the nodes, which leaves two lists pointing at the same memory. I avoided that particular trap by building a copyFrom() helper that walks the other list node by node and calls pushBack() to create brand new nodes, but I ran into a different, sneakier bug later when I went back to add comments to my code. In my remove() and contains() functions, I had written "if (current->data = value)" with a single equals sign instead of "==". That is assignment, not comparison, so the condition was always true and it was silently overwriting the node's data every time instead of checking it. The code still compiled fine with no warnings, and my early tests did not catch it, because I had tested pushBack, the copy constructor, and the iterator thoroughly, but had not specifically verified remove() or contains() worked correctly on a value that should not be found.

I caught the bug by rereading my own code line by line while writing comments explaining what each part did, which forced me to actually think about what each line was supposed to do instead of just skimming it. Around the same time I noticed popFront() was entirely missing from the file, which must have gotten lost somewhere while I was retyping it by hand on the server after an earlier typo-filled attempt. Once I added it back in and fixed the == bug, I recompiled and reran my existing tests, then later went back and added dedicated test cases for popFront, remove, contains, size, isEmpty, and both copy operations, including edge cases like calling these on an empty list.

If I started over, I would write a small test for every single function as soon as I finished writing it, instead of mainly testing pushBack and the copy constructor and assuming the simpler-looking functions like remove and contains were fine just because they compiled without errors. I would also be more careful typing code directly into nano on the remote server, since most of my bugs came from small typos and dropped characters rather than actual logic mistakes.

What I understand now that I did not before is that a program compiling cleanly, even with -Wall and -Wextra, does not mean it is correct. The = versus == bug is exactly the kind of mistake a compiler will not catch on its own, and it only surfaced because I happened to reread the code carefully. I also have a much clearer picture of why the Rule of Three matters for anything that manages its own memory, not just as a rule to follow, but because of what actually breaks if you skip it: two objects silently sharing memory they both think they own.
