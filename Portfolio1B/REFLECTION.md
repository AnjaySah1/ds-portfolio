#Reflection - Portfolio 1B (Undo/Redo Text Buffer)

I built the Stack<T> class first, since TextBuffer depends on it, then designed the UndoRecord struct, then wrote TextBuffer itself, and finished with the command loop that reads TYPE, DELETE, UNDO, REDO, and PRINT. I decided early on to keep the document model simple: TYPE always appends to the end and DELETE always removes from the end, with no cursor position to track, which matched the hint in the assignment to keep it simple rather than modeling a full text cursor.

The hardest part was getting Stack's operator= right. While typing it into nano on the server, I accidentally left the function incomplete: it only had the self-assignment guard and never actually called clear() and copyFrom(), and it was missing its closing brace entirely. Because that brace was missing, every function I wrote after it in the file, push, pop, and top, ended up accidentally nested inside operator= instead of being their own separate functions. The compiler error was confusing at first because it reported that my test file's main() was somehow a member function of Stack, which did not make sense until I traced the braces back far enough to find the one that was missing. I also ran into a smaller but similarly confusing bug in undo(), where I had accidentally typed { else { instead of } else {, which broke the if/else structure in a way that was easy to miss just by glancing at the code.

I found both bugs by compiling often and reading the error messages carefully instead of assuming the first error listed was the real problem. The missing brace especially caused a long chain of unrelated-looking errors that all traced back to one spot, so I had to work backward from the first error rather than trust the later ones. Once I fixed the structure, I retested by typing a sequence of TYPE, UNDO, REDO, and DELETE commands by hand and checking the printed document matched what I expected at each step. Later, after my professor's feedback on Portfolio 1A about testing not being thorough enough, I went back and expanded my test command file to also cover undo and redo with no history yet, deleting more characters than exist in the document, and a new TYPE clearing the redo stack after an undo, which are all cases my original tests did not check.

If I started over, I would double check brace matching right after writing each function instead of writing several in a row, since one missing brace cascades into a lot of confusing errors further down the file. I would also build out my edge case tests from the start instead of only after getting feedback that my testing was not thorough enough.

What I understand now that I did not before is why undo and redo pair naturally with a stack: reversing the most recent action and being able to reapply it both fit push and pop order, which is part of why real text editors are built this way. I also have a better sense of how much a single misplaced brace can cascade into seemingly unrelated errors, and why reading compiler errors from the first one down, rather than the last one up, is usually the faster way to actually find the problem.
